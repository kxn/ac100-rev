# 原固件中的异常行为、原因判断与Go处理

仅讨论已经读到的V4 1.4.3与提供的V6代码。事实来自原ELF/调用指令；关于作者意图、为何测试没覆盖或为何未修的解释是推测，不代表厂商说明。尤其不能据1.4.3断言用户的1.4.4也未修。

## 可以确定的缺陷：Go不复制

| 行为与影响 | 证据 | 原因与可能被遗漏的条件 | Go处理 |
| --- | --- | --- | --- |
| V6某客户端无有效邻居时，沿用同一包中上一客户端的候选，可能跨客户端/服务串用 | `roam_nbr_select@4e5638`在`4e577c`提前返回，跳过`4e5aac`输出数量清零；调用循环`4e6ba0`只每包初始化 | 确定原因是输出变量生命周期大于单客户端。推测单客户端测试或每客户端都有邻居时看不出，必须覆盖“前一个有、后一个空”的同包组合 | 已移除包级候选复用；每个客户端独立结果。合同`roaming-packet-output-state` |
| V4共同信道ACS找不到另一5GHz频段时，临时结果可能仍是之前的overall-best5 | `wsta_roam_chnl_handle_thread@4857a8`正常BSS分支在搜索相反频段前未清输出 | 确定原因是复用临时变量。推测仅一个5GHz频段有有效样本时容易触发；同时有低/高段样本的测试会掩盖 | 已独立清空该输出，再使用源码已有36/149默认值；有样本时排序不改。合同`v4-acs-empty-opposite-band-output` |
| V4 PMK operation3返回密钥成功，但关联同步实际没有发生 | `4871ac/4871b0`给关联函数第9参数传NULL；`632740/632754`立即拒绝，调用者忽略结果。V6改为有效输出地址 | 确定原因是调用参数与被调函数契约不符。可能是关联API新增输出参数后旧调用未同步；若AP随后又发普通关联/清单，上层观察可能最终恢复，掩盖即时同步失败。这些开发历史与掩盖条件是推测 | 保留有效特殊同步，不加普通准入，不复制NULL参数。合同`v4-pmk-special-association-null-output` |

三项都保留原代码证据与明确的有意差异，不把修正后的行为说成原固件逐字实现。

## 可疑但不足以擅改策略的行为

| 行为 | 判断与可能原因 | 当前处理 |
| --- | --- | --- |
| V6弱信号回退使用筛选循环最后访问的频段门限，却挑排序第一项；两项可能不同频段 | 代码事实明确，属于较强的变量残留疑点；可能是把循环局部变量当首候选信息，造成跨频段边界不一致。仅凭代码无法证明作者要取哪一项的门限 | 保留原比较，不自行换首项门限。其余正常筛选与最终候选不变 |
| V4低负载AP重分配的2G输出只有6/11/0，0表示不改；5G只可能40/48/153/161 | 查表起始地址偏移1，随机数先乘10再取余/低位，因此不是均匀覆盖完整数组。很像旧随机缩放和下标组合造成偏差，但其中0可能是有意保留信道；没有“正确新分布”的源码依据 | 保留原uClibc和uint32回绕/查表，不自行发明均匀轮转 |
| 上述重分配对每台AP重新`srand(time(NULL))`，同一秒处理的多台AP通常得到相同信道对 | 会削弱不同AP间随机分散的效果。可能是播种位置过近，也可能只是用时间扰动统一共同信道后的配置；原代码不足以证实意图 | 保留逐AP播种。可疑算术和播种位置与AC共同信道模式是两件事，不把推测当成新调度策略 |
| 活跃统计把未知速率`0xffffffff`也算作`>1`，离线行在905秒后随60秒扫描删除 | 可能是“未知就按活跃处理”的保守保护，也可能是有符号哨兵与无符号比较带来的副作用；代码没有解释。这会使新上报不足或刚离线的AP更难满足重分配条件 | 保留包含idle的原始统计判断，不能擅自改成只数在线客户端或把未知按0处理 |
| V4旧平滑TPC在匹配特定邻居AP ID时出现空循环，循环内没有推进列表指针 | `run_smooth_TPC@4b1a04`的反编译暴露潜在不退出分支；其调用受`_rrm_task`内部开关约束。未在实机运行，未证明某实际配置会到达，不能直接宣称所有V4优化都会卡死 | 仅列为疑点；Go可分别选择V4 DCA/TPC与V6 SCA/TPC；原内部平滑TPC的调试开关默认为0，Web/JCS无启用字段，未将疑似不退出分支开放为产品选项。该模块的版本边界已在跨版本复核中明确 |

以上疑点与确定的输出串用/NULL缺陷不同：改变它们会直接选择另一条无线调度策略，目前没有擅自改动。

## 看起来反常，但有合理设计解释

| 行为 | 可能目的、代价及当前处理 |
| --- | --- |
| 自动模式从高性能退到兼容后，负载降低、离线或重启不会自行升回；需要手工改选 | 很可能是单向保护和避免频繁切信道/模式震荡。代价是名字叫“自动”却不双向自适应。保留；Web展示配置模式和实际模式 |
| AP数超限只回退模式，STA数超限还检查并重分配低负载AP | 合理解释是新增AP时避免立刻打断其它AP，客户端规模超限时再拆散共同信道；这些是两条源代码入口，不是遗漏一个公共调用。保留 |
| V4均衡按MAC记录计数，MLO客户端会因多个peer更早达到人数门限；V6改为只算逻辑客户端 | 计量单位不同。旧版本可能把链路负担计入AP负载，V6明确改为逻辑人数；不能仅凭“一个平板”就断言两版都应计1。按两版实际回调分别实现，不把所有重复记录都认定为确定bug |
| V4先选5G，即使2G估算率更高；未知率有时排在已知率前面 | 体现频段偏好及“估速不确定时看RSSI差值”的旧策略，目标不一定是全局最高瞬时速率。V6换了全局速率排序，属于发布版本策略演进；不能混成一个算法 |
| V6当前信号极弱时，回退可以绕过正常负载和速率增益过滤 | 合理解释是先离开糟糕链路，接受不完美目标。若重新加回这些过滤，可能反而永远无法脱离弱信号。保留；上面的“取最后频段”另列疑点 |
| PMK请求失败会释放客户端在旧AP的关联，而不只向请求AP回复失败 | 可能是失败时清理旧位置/漫游状态的保守策略，但可用性代价是一次失败查询可能影响旧连接。两版都有这条清理链；保留原AP、原radio和整组MLO语义，不另加自己的宽容路径 |
| BSTM邻居RSSI统一再减10dB；V4当前信号不按首项自身测量修正，V6会修正 | 邻居余量可能为测量偏差和回连抖动留余地；当前基线的改变属于版本差异。不能将两者当作同一RSSI直接比较。按各版本保持 |
| 两版估速表相同，活跃候选却分别用-95/-85信号基准；缺统计的PHY默认也差很多 | 估算模型的假定变了，同一输入可以得到不同排名。可能是保守程度或校准变化，但不能仅凭代码证明哪个更接近实际链路。按来源选完整输入语义，不因表相同就共用错误基准 |
| V4估算器不认识BE射频配置模式12/13，落到HT；V6增加EHT分支 | 是明确的旧版本能力限制/保守回退；不能由此推断V4的所有WiFi7配置都不可用。它会影响估速，故单独列出；V4保持原分支，V6采用原EHT分支，不暗中将一个新PHY映射混进旧算法 |

## 为什么之前Go没有发现这些偏差

此前对候选、估速和PMK的证据集中在V6活跃路径。V4模式控制补入后，没有同时把V4注册根及实际调用链闭合，因而漏了：V4仍调用旧选择器、不同信号/PHY输入、伪关联入口，以及均衡对57策略字节的消费者。这个遗漏是Go审查不完整，不能归因于备份没有启用、AP没有上报或原代码不存在。

本次把来源选择集中到完整策略族，再做V4/V6注册与反向引用比对。还修正了Go自动计数把AP-entry角色7误写成原始ProductType7的问题；这是Go实现错误，不记作原固件bug。

固件的真实开发历史和测试覆盖未知。上面对“为什么原厂可能没发现/没修”的解释均为条件推测；能确认的是具体控制流和后果，以及V6中部分调用已经不同。完整差异与验证命令见[双向复核记录](cross-version-mobility-review.md)。


## 本轮独立RRM复核补充

- V4双5GHz设备的第一组禁用位取决于**物理**第二5G候选域的数量；不是按信道数值逐一做互斥比较。原Web按低段在前、高段在后的顺序构造候选域，因此自行改候选顺序会影响结果。Go保留原位规则及输入顺序，没有改成另一个偏好算法。
- V4 DCA的邻居累计使用16位成本，而选根比较按有符号short；原始RSSI重复样本继续累加。Go保持这些运算，未擅加V6的RSSI截断、平滑或新的溢出饱和策略。
- V4 TPC在每步后取最近硬件功率档位，量化可能回到搜索的排他边界。例如硬件3–24、搜索上界24、计算目标23会量化到24。这个边界用于搜索收敛，初始配置/硬件范围另行量化；缺少依据将最近档位改成向下取档，故保留原逻辑，不把这种效果未经论证就定性为需要修复的bug。

此前Go让V4高性能ACS后继续V6功率阶段，是Go的版本拼接错误；原pwr_rrm_start明确要求实际模式2，已经修正。物理功率11/12/13元数据的遗漏也属于Go能力解析缺口，已在共享能力视图修正，避免编辑、校验、下发档位和优化各用不同单位。
