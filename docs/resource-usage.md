# CPU 与内存资源审查

本轮以独立 Go UAC/Web 为范围，检查后台协调、AP 状态快照、配置继承、历史保留/保存/查询、固件上传/分发及 Web 轮询。保留原固件的参数、优先级、触发门限和协议计时，不以改变 AP 调度行为来降低资源占用。

## 实施

- AP 遥测快照用明确的类型拷贝替代 JSON 编码/解码；复制嵌套映射、原始 JSON 数据和可选值，保持与实时 AP 数据隔离。客户端列表只读取 AP 在线标志，避免为在线判断再次复制完整遥测。
- AP 参数与射频继承使用类型明确的覆盖操作。保留 nil 继承、显式 false/0、空列表的 omitempty 行为、完整嵌套对象替换、EDCA/DCS/接入控制回退、绝对功率与功率等级互斥；结果拥有独立的嵌套数据。测试逐字段对照原 JSON 覆盖语义，并检查修改结果不会污染输入。
- 历史记录跟踪最早到期时刻；新记录增量维护到期索引，容量超限或真正到期时才清理，继续支持乱序时间戳。清空丢弃记录在切片尾部的引用，大幅缩小时释放大数组；过期的采样索引一并移除。
- 历史查询从尾部收集满足过滤条件的结果，到请求数量后停止，再恢复原顺序；不会先复制完整记录后再截取。离开管理锁后编码响应。
- 历史快照逐条流式写入，缓冲 32 KiB；其它内部 JSON 使用紧凑编码，保留临时文件、fsync、原子 rename 的事务。落盘格式仍是 JSON，原数据可直接读取，失败的保存保留旧文件。
- 固件上传先流式写入临时文件；镜像检查基于 ReaderAt，顺序计算完整 SHA-256/MD5，仅读取所需头部/元数据。下载以 1 KiB 协议块从同一文件描述符读取，大固件分段 MD5 也使用流式读取。保留镜像大小/分区/支持型号检查，以及发送前完整性、AP 应答、最终校验与重连版本确认。标准现代固件路径不为每台 AP 保留完整镜像。
- Web 在后台页签暂停四秒轮询，重新可见时立即刷新；后台 AC 协调和 AP 计时不变。
- Docker 两种镜像默认 Go 软预算 GOMEMLIMIT=64MiB；Compose 的 AC_GO_MEMORY_LIMIT 可覆盖。没有固定 GOMAXPROCS，也没有在程序中引入定时强制 GC。

完整配置 snapshot 继续保留 JSON 深拷贝，其共享对象隔离覆盖所有配置种类；32 AP/64 射频夹具约 0.44 ms/次、91 KiB 分配。这次没有为了减少这一较小的周期性开销引入覆盖所有策略类型的缓存或省略字段。

## 可复现基准

Go 1.26，Linux amd64，AMD Ryzen 9 5950X。每项运行三次，下表取中位数。耗时受主机负载影响，不能视为 RouterOS/ARM64 真机结果；B/op 是每次 Go 堆分配，不是进程 RSS，也不包含文件页缓存。

| 路径与夹具 | 优化前/整块读取 | 优化后/流式读取 |
| --- | --- | --- |
| AP 参数继承（32 AP 配置，含模板/分组） | 89.5 µs，27,024 B/op | 1.63 µs，1,456 B/op |
| 射频覆盖 | 18.1 µs，5,172 B/op | 0.137 µs，336 B/op |
| AP 遥测快照（双频、16 VAP） | 37.9 µs，17,417 B/op | 4.12 µs，10,464 B/op |
| 历史空闲检查（2 万射频、10 万信号、1 万事件） | 874 µs/次扫描 | 初始化到期索引后 0.031 µs/次检查 |
| 32 MiB 现代固件读取与完整校验 | 51.6 ms，33,604,255 B/op | 47.5 ms，36,610 B/op |
| 2 万条射频历史序列化 | 30.1 ms，14,733,219 B/op | 15.9 ms，2,435,989 B/op |

固件表项在同一个新校验器上比较 os.ReadFile 与 ReaderAt 路径，隔离整文件缓冲带来的分配；没有声称 36 KiB 是整个升级任务或整个程序的峰值。历史空闲行不包括新采样、真正到期和落盘时仍需做的工作。

## 验证范围

- Go 全量测试、go vet，以及 admin/cweng/firmware 的 race 检查通过。
- 固件解析器模糊测试通过；现代/旧式镜像、损坏校验、被移动的设备头、截断文件、大小边界均有覆盖。既有升级回归继续覆盖普通镜像及超过 16 MiB 的分段协议、应答、最终校验和重连确认。
- 配置覆盖的逐字段参考测试、快照数据隔离、历史清理/乱序/查询限额、流式 JSON 等价与失败原子性通过。
- 原固件双向索引通过；47 项行为契约中的 128 个命名测试通过。这是指定分支回归，不是所有固件行为等价的证明。
- Web 两组 AP 能力条件各 23 页、共 54 次表单提交通过；后台停止轮询与重新可见后刷新纳入回归。
- Linux amd64/arm64 的有 DHCP、无 DHCP 镜像已重建；两平台各执行无 DHCP → 有 DHCP → 无 DHCP 的启动、发现、配置持久化、退出检查，确认软预算环境。amd64 在 128 MiB 容器硬限制下执行；arm64 为 QEMU 仿真，没有 RouterOS 真机资源数据。

单 AP + 一个客户端的部署前读请求采样：20 秒内主动发起 15 次只读管理请求，平均 RSS 24.94 MiB，CPU 约单核 0.089%。这个低负载样本只作运行基线，优化收益主要由可重复基准和较大历史/固件场景证明。

部署后用同样的 20 秒、15 次主动只读请求采样：平均 RSS 23.03 MiB，CPU 约单核 0.072%；AP 和一个平板均在线，10 项配置应答确认、3 项回读一致，平板网关、DNS/HTTPS 检查通过。短时 RSS/CPU 受 GC、采样阶段及浏览器请求影响，不将这两个单 AP 样本当作通用节省比例。

另在 Linux amd64、Go 软预算 64 MiB、容器硬限制 128 MiB 的空载容器执行 32 MiB 合成固件的真实 HTTP 上传/校验/删除，进程 VmHWM 17.37 MiB。此样本没有 AP/客户端，不等同于满载容器或 RouterOS 设备需求。
