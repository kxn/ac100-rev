# 漫游路径再次双向核查（2026-11-27）

> 后续V4/V6双向复查已把来源扩展为完整候选/估速策略族，PMK确定缺陷单列修复。当前两族对应关系见[跨版本复核](cross-version-mobility-review.md)，本文其余内容记录V6基线。

> 本文记录V6基线。2026-11-27新增的V4固定高性能模式是独立、有来源标记的扩展，入口/ACS/RRM和版本边界见[补充对照](v4-high-performance-reference.md)；本文关于只开放模式2的陈述只适用于V6基线。

对照用户提供的 TL-AC100 V6.0 1.0.3 Build260817 Rel.68871n。UAC SHA256 固定为 `b12d1584fcafda2a71aa9038b41b7e1c5b893b350f3e6edf5105e445d024a912`。本轮只用静态代码、反汇编调用点、配置描述表和本地 Go/模拟 AP 回归；不运行原 UAC，不用实机现象推导或证明原算法。

上一轮的实现和说明仍有遗漏，不能把其测试通过作为本轮结论。本轮沿入口→数据库→选择→打包→发送→失败清理检查，再反查 Go 决策的来源。

### 原代码的包内输出残留：明确修复的厂商缺陷

这不是推断的厂商策略意图。MIPS指令事实是：

| 地址 | 指令/含义 |
| --- | --- |
| `4e6ba0` | `sw zero,0xc20(s8)`，结果包创建时初始化输出数 |
| `4e713c/4e7140` | 调用`4e5638`，a3指向同一`sp+0xc20`输出数 |
| `4e577c` | `0x52400267`，邻居计数为0就返回`4e611c` |
| `4e5aac` | `sw zero,0(s5)`，到达排序/过滤阶段才清输出数 |

原代码中，后一站点零有效邻居时可能复用前一站点候选；有邻居但全部筛掉才清空。这是厂商缺陷，不能当作调度策略。按用户本轮明确要求，Go删除共享的`lastSelection`，始终为每个客户端独立调用选择器。没有有效邻居就返回空列表；AP bitmap、历史记录和序列化后的59都不再带入其它客户端候选。原指令证据保留，行为合同改为`firmware-bug-fix`并记录授权，不能隐瞒这项有意差异。

本轮新增跨无线服务、无法解析BSSID、冲突信号编码、130站点分包和真实Go UDP监听→59下发回归。把修复前实现临时放回，这四项相关测试均失败；恢复修复后通过。选择器本身及其排序、负载/信号/增益门限、弱信号回退没有修改。

### 反向检查 Go 自有部分

以下属于独立程序的架构和传输适配，不冒充原候选算法：会话epoch、非阻塞命令队列、ACK状态、配置持久化与AP缓存提交、JSON型号适配、Web规则编辑及资源预算。它们不能给候选额外加人数/MAC排序、ACK冷却、SSID猜测或“最强AP”兜底。本轮移除了发现的猜测入口，收敛了统计事实所有权。

25控制57/59，72控制9d；Go按当前配置收敛，在AP重连后恢复所需参数，不宣称它的goroutine组织和原UAC事件分发完全相同。默认静默控制可在“默认漫游参数→AP漫游静默控制”编辑，计数8位、秒数16位，API如下：

```json
{"silence":{"count":3,"seconds":30}}
```

这是`/api/mobility`完整配置中的一个字段；保存时保留其它字段。原Flash没有提供的值只标注为Go初值，不以猜测填补“原机具体值”证据。旧模式0/1、高性能静默参数和ACS超时字段未扩展为V6可开启策略。
