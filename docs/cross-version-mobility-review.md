# V4 1.4.3 / V6 漫游策略双向复核

基准为官网下载的 **TL-AC100 V4.0 1.4.3 Build240715 Rel.80898n** 与用户提供的 **V6.0 1.0.3 Build260817 Rel.68871n**。V4 UAC SHA以`ddc30fd8…`开头，V6以`b12d1584…`开头，完整摘要及地址见 [跨版本证据](cross-version-mobility-evidence.json)。没有执行原UAC，没有用实机或外部黑盒测试推导算法。1.4.4仍未取得，不能把本结论外推为该版本逐函数等价。

## 结论与实现选择

上一轮“V4模式控制 + V6候选/估速”的组合存在真实策略偏差。V4实际调用的选择器，在V6中已经成为无调用入口的旧代码；不能因为名字相同就当成两个发布版本的活跃路径相同。

现在由同一个固件策略来源选择模式控制、候选选择、PHY回退、估速、关联结果和参数消费者：

- `mode_source=tl-ac100-v4-1.4.3`：使用V4分支，适用于配置模式0/1/2。自动模式回退为实际2后仍保持V4选择器。
- 新建配置明确标记V6来源；已有未标记来源的兼容模式2继续使用V6分支。此前未标记的Go原型0/1保持既有迁移规则。
- V4.0备份导入也保留来源，包括源配置本来就是固定2的情况。显式转换模式不等于改换固件策略来源。
- `mobility.Policy`集中处理版本差异；V4选择器单独实现。共用的编译速率表、统计数据结构和PMK流程有两版证据，不用若干局部常量把两个选择器拼起来。

| 均衡影响漫游参数 | `balance_init@4590a8`注册`balance_roam_strategy_get@457f90`；开启时策略2→1，`482d04`更新并重发 | 没有该注册，策略保持2 | 根据AP有效均衡设置构建完整参数；策略字节进入应用签名，切换后确实重发57 |

V4伪关联的容量比较是严格`count < max`，不会因为当前MAC已在目标射频而豁免。只有容量通过后才运行服务和均衡回调；均衡可以消耗共享拒绝次数。RADIUS、Portal等已排除的认证回调不引入程序。

## 候选算法不能混用的细节

| 项目 | V4 | V6 |
| --- | --- | --- |
| 排序范围 | 5GHz单独排序并优先取，再处理2.4GHz | 先5G后2G拼接，再全局排序 |
| 已知率排序 | 速率降序；同速率无额外RSSI比较 | 速率、频段、RSSI依次比较 |
| 未知率-1 | 两个未知按RSSI；未知与已知按RSSI差值分支比较，不直接全排最后 | 正常筛选拒绝-1，仅可能进入弱信号回退 |
| 兼容态绝对门限 | RSSI触发位开启时用配置门限，否则2G -75 / 5G -80；要求严格大于；负载不超过70/85 | 配置类型含RSSI位时使用固定-85/-87，否则-75；边界允许相等；负载不超过70/85 |
| 高性能态绝对门限 | `_nbr_filter`跳过上述绝对RSSI和负载检查，方向差值仍执行 | V6产品Web只开放兼容2，不把旧内部模式分支拼入 |
| 方向差值 | 同频段减配置差值；5→2再减编译常量5；2→5不额外减差值 | 正常路径要求估速至少提高20%且至少增加20Mbps |
| 无正常候选 | 无单独V6式弱信号兜底；无候选的客户端不进入59结果 | 当前信号严格低于-85时可取排序首项；可以输出空候选行 |
| 输出数量 | 调用者传6，但再被编译上限4截断 | 编译上限4 |

两版都保留原quicksort的同分顺序。V4排序比较器还会标记不合格索引，单邻居也需调用一次比较器；不能先换成另一种稳定排序或过滤后排序。

## 估速：表相同，不代表调用语义相同

两版**560字节的SNR表与80字节带宽乘数表逐字节相同**，因此Go共用生成表。整数斜率先截断、16位结果、取终端/射频能力的最小组合及保留终端MCS的运算一致。

| 项目 | V4 | V6 |
| --- | --- | --- |
| 活跃候选信号基准 | `48b644`使用RSSI+95，RSSI≤-95返回0 | `4eb314`使用RSSI+85，RSSI≤-85返回0 |
| 2G无有效终端统计时 | 20MHz、1流、HT、MCS7 | 40MHz、1流、EHT、MCS7 |
| 5G无有效终端统计时 | 80MHz、2流、VHT、MCS9 | 160MHz、2流、EHT、MCS9 |
| AP自动PHY识别 | AX→HE、AC→VHT；不识别BE配置模式12/13，按原默认HT回退 | 增加BE→EHT及模式12/13 |
| Mesh角色 | 允许0..4/6/8；4/6/8用WiFi和当前回传率的串联公式 | 同样的角色及公式 |

`get_estimate_by_stat`是另一个估速消费者：使用统计中的实际NoiseFloor，缺失时回退-95。其反向调用者在两版都是`_cloud_mngt_online_client_event_object_add`，属于用户排除的云事件；不能误当作候选算法入口。`estimate_airtime`在本次Ghidra反查中没有引用。二者已记录来源和分类，不因名字相关就给程序增加云功能，也不把这个入口的NoiseFloor公式挪进候选估算。

## PMK共用的依据与确定缺陷

两版都支持operation0通知、1查询、能力66限定的3特殊查询；先查MAC缓存，再查目标服务，缺密钥结果1优先于无效槽位结果2。同逻辑服务重关联取消删除；离线保留60秒、分钟扫表；查询失败释放数据库中当前所在AP的整组关联，再向旧AP发删除站点命令。密钥不进入Web或备份。

**不能把operation3的关联副作用说成完全相同。** V4 `4871ac`调用`uac_wstation_assoc`，延迟槽`4871b0`把第9参数写NULL。被调函数`632740`加载该参数，`632754`为空即返回失败。调用者忽略结果后仍返回PMK成功。V6 `4e4a14/4e4a24`提供有效局部输出地址，修正了这个问题。

按“不复制明显bug”的要求，Go在V4族也进行有效的特殊关联同步，沿用旧RSSI、无旧条目时用0，不叠加普通均衡检查。这是有意修复，合同为`v4-pmk-special-association-null-output`；没有伪装成对原错误行为逐字复刻。旧AP删除/MLO清理及其他PMK分支不改变。

## 入口闭合范围与验证

从注册根重新导出：V4 10根、72处地址引用、71个回调；V6 11根、96处引用、95个回调。V4没有V6漫游SQL规则根；Go已有规则功能保留为功能超集。两版各另检查4个统计定时器表项。反向搜索本次目标得到V4 14处、V6 11处引用，与全符号范围J/JAL直接分支枚举相符，包含零引用旧目标。V6此前较广的模式审查仍另保留2处foreach指针证据，数字不能混作同一目标集合。

V4回调中唯一在V6入口分类中不存在的名字是`balance_roam_strategy_get`，已补齐它的消费者、更新入口和重发。PMK特殊同步、一般关联/清单同步、RSSI/BSTM、统计有效性、AP离线和配置变更分别归类，不依赖这次备份是否启用。另修正自动AP计数将原AP-entry角色7误作原始ProductType7的问题：sensor原始产品类型2才映射到角色7。

复查Ghidra集合时，可给审查器传`--reference-directory`，目录内是两版的`*-entries.tsv`与`*-reverse.log`。TSV用`ExportEntryReferences.java`按证据清单列出的注册根导出；反向日志由`FindCallers.java`按清单目标导出。均为只读`analyzeHeadless`分析。审查器比对集合、ELF摘要、函数字节、指令、调用者、表项及两版编译表，不运行固件或接触AP。

本轮新增的分支回归覆盖版本切换、V4自动回退后不换算法、强当前信号/未知率的分歧、容量/均衡伪关联、BSTM当前基线、PHY默认/信号基准、均衡57策略重发和关联结果码。PMK的实报文回归扩展到两族。合计59项合同、190个命名回归已执行通过；这说明已识别分支有证据和回归，不是穷尽语义等价证明。未部署、未改运行AP。

## 独立射频优化的版本边界

客户端策略和独立RRM现已按功能分别选择。`mobility.mode_source`选择客户端策略族，`rrm[].strategy_version`选择该规则的V4 DCA/TPC或V6 SCA/TPC；不存在全局切换，也不再让V4 RRM暗中使用V6库。V4独立`_rrm_task@4aef30`与`run_DCA@4b07f8`/`dfs@4b0180`、`run_TPC@4b1750`已单独实现，分组、报告、功率轮次及失败应用有各自证据。高性能ACS后仍为模式1时不启动TPC，修正了旧Go错误接续V6功率阶段的行为。

入口、配置、版本约束及源函数对应见[按功能选择策略版本](component-strategy-versions.md)；完整静态RRM指纹见[v4-rrm-evidence.json](v4-rrm-evidence.json)。V4的云事件估速、独立RRM和客户端候选虽然共享数学辅助函数，仍按不同入口归类。
