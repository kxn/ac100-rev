# AP 信号与速率上报交叉核查（2026-11-28）

本轮将 AP 型号、固件版本、接口和字段分别核对。不能因为某条 JSON 有正信号就声称所有 AP、所有接口、任何时刻都只报正值，也不能用“是否进入漫游”替代字段来源的解释。

固件包、解包文件和生产报文不进入仓库。重新准备样本时，将官网ZIP保存到索引指定位置，提取其中BIN，按 `squashfs_offset` 用 `unsquashfs -o` 解包；索引同时记录BIN名称和摘要。公开的[证据索引](ap-reporting-evidence.json)记录下载地址、压缩包/二进制摘要、函数范围以及 JSON 字段名的常量引用。核验命令：

```sh
python3 tools/audit_ap_reporting.py
```

这个命令验证两份官网下载文件、三份 ELF 和25处函数范围及8个字段名引用，不执行原固件，不对 AP 发命令，也不声称摘要匹配就证明全部逻辑等价。

地址口径：3007 DMS 是 `ET_DYN`，本轮 Ghidra 分析重定位到零基址，文档中的 DMS 地址均为原 ELF 地址。内核模块使用 `.text` 段内偏移，不拿 Ghidra 分配的运行地址直接当文件偏移。复核脚本按 ELF 段表/节表读取，避免基址偏移导致分析到另一个函数。

## 信号为什么有正有负

### 3007 GC：原生 JSON 与 CAPWAP 是两条生成路径

原生 `wireless.sta_list.rssi`：

1. DMS 的表收集函数 `@25f73c` 通过 `wlan_ioctl_get_sta_info_ext@30a804`、驱动 `get_station_info` 获取记录。
2. 信号取驱动记录偏移 `0x0c` 的**无符号字节**，保存到 DMS 记录 `0x90`。
3. `wlanStaListReadJson@25fdcc` 将该值直接格式化到名为 `rssi` 的 JSON 字段，没有减95。

驱动的 `node_getsnr` 读取的正是相同节点偏移 `0x36c`，确认这条原生字段属于SNR口径，不能仅凭字段名理解为负 dBm；该版本收集代码对它做了无符号字节扩展，所以这条输出本身不会为负，零值仍有可能。

CAPWAP `0x52` 的信号：

1. 统计采集使用另一条驱动接口 `get_station_stat`。
2. 驱动调用 `wlan_node_getsnr` 后减95，并将正方向限制为0，再存为有符号信号字段。
3. DMS `getStationData@210358` / `GetPrivStaStatistics@a0184` 收集此值，由 `CWAssembleStaStatisticsMsg@8cb40` 写到38字节记录偏移10。

因此，同一台 3007 可以同时发送原生 JSON 正值和 CAPWAP 负值。这不是 Go 丢负号。两条路径读取的缓存/时刻也不同，不能拿不同时刻的数字机械相减后反推一个通用换算。

### Wi-Fi7 AP：原生 JSON 自己做了减95

该版本 `wlanStaListReadJson@2f6830` 在输出相同名字的 `rssi` 字段前减95；其收集函数是 `@2f6240`，使用不同的驱动记录格式。不能将 3007 的无偏移输出规则套到它，也不能把 Wi-Fi7 的规则直接套给未知 AP。

本轮保留抓包中，能完整解码且唯一关联到现场两台 AP 的样本如下；这是本次有效样本统计，不是所有历史和所有设备的无限覆盖。

| 来源 | 有效样本 | 正 / 零 / 负 | 范围 |
| --- | ---: | --- | --- |
| 现场3007，原生 `wireless.sta_list.rssi` | 25,722 | 25,722 / 0 / 0 | 7～75 |
| 现场3007，CAPWAP `0x52` 信号 | 6,835 | 0 / 0 / 6,835 | −88～−20 |
| 旧实验网Wi-Fi7，完整未分片 `sta_list` JSON信号 | 2,908 | 0 / 0 / 2,908 | −23～−19 |

旧实验网确实有原生负值。“原生信号都是正的”不是正确的跨型号结论。生产报文无法唯一关联、或者落在日志缺口中的记录不纳入这张表；私有分析保留匹配/丢弃计数，不能强行把歧义报文归到某台 AP。

## 3007 的速率零值来自哪里

### CAPWAP 协商速率在 AP 里被明确置零

3007 的 `GetPrivStaStatistics@a0184` 对每个客户端执行：内部记录偏移 `0x0c` 的16位值置0。`CWAssembleStaStatisticsMsg@8cb40` 将它原样作为 BE16 写到线记录偏移12。

本轮6,835条完整有效 `0x52` 记录的这个值全部是 `0000`。因此，它不是 Go 偏移读错，也不是大小端解析导致；这版 AP 的 CAPWAP 发送实现没有提供协商速率。不能通过重复下发统计开关让一个无条件置零的字段变成真实速率，也不能把0当成实际零速 Wi-Fi 链路。

Wi-Fi7 的 `GetPrivStaStatistics@e0e08` 则从已采集数据复制该字段，没有上述无条件置零。旧抓包能读到1201、600、573、864、1080等值，这解释了之前设备显示正常的差异。

### 原生 TX/RX 是另一个量，不能填进协商 Mbps

3007 原生 JSON 的 `tx_rate/rx_rate` 来自驱动 `get_station_info` 的偏移 `0x28/0x2c`，分别调用 `wlan_node_gettxdatarate/getrxdatarate`。这两个函数读取节点的周期统计值；`ic_calc_txdatarate_timeout` 调用 `update_txrx_ratekbps_iter_cb`，根据收发字节计数差计算值，计数没有增长就得到0。

它们是实时流量速率，不是 PHY 协商速率。真实 Wi-Fi 连接已经建立而流量为零时，出现0是正常的。`get_station_stat` 里查询 PHY 的 `wlan_node_txrate_info` 是另一条调用，不能因为都叫 rate 就当作同一个字段。

旧 Go 代码取 `max(tx_rate, rx_rate)`，按16位整数塞进 `NegotiatedMbps`，有两个错误：混淆量和单位；大原值超出16位时忽略解析错误。这会把3007的低流量显示成1～3 Mbps协商值，并与随后真实的零占位统计交替；不是 AP 的无线连接在这些速率之间跳变。

## Go 的修复边界

- 原生 TX/RX 放到独立的 `native_rates`，保存两方向原值和采样时间，不覆盖 CAPWAP 的协商速率、带宽或流量计数；不按实验型号列白名单。
- 协商值为0时，页面显示“协商未上报”；有合法正值的设备继续显示实际 Mbps。实时上/下行速率单独显示，合法的空闲零值仍显示0。
- 客户端列表只显示统一的 CAPWAP dBm 与协商/实时速率。原生接口原值移到客户端“信号详情 → AP 原始上报（调试）”，明确标注“接口原值”及采样时间，不为未知固件猜单位。没有统一信号则显示“未上报”，不拿原生字段冒充。
- 快照保留旧 CAPWAP 事实时要求同一连接、位置、服务且仍在线，避免重连后沿用旧信号和速率。

回归覆盖3007式零协商值、Wi-Fi7式有效协商值、原生低流量/零流量、超过16位的原值和会话切换，并在页面同时检查有效速率与“未上报”的展示。当前协议没有给出的3007协商值仍然未知；没有用估算值或旧客户端的值填补。

## 信号怎样进入调度，哪些转换确实存在

页面常规信号、原生诊断和当次调度输入各有来源，不能因为同一客户端同时存在三个数就认为应该用其中一个覆盖另外两个。

| 数据路径 | Go 的消费者 | 换算与用途 |
| --- | --- | --- |
| 原生 `wireless.sta_list.rssi` | `mergeWirelessSnapshot → ClientNativeSignal` | 保留原值，供诊断；不写入 dBm、RSSI 邻居表、PHY 能力或候选估速 |
| 关联/客户端 CAPWAP RSSI（含 `0x52`） | `ClientTable`、客户端列表、信号历史 | 按协议有符号值保存；原生快照不改其值和采样时间；页面统一采用此口径 |
| `0x58` 当前客户端信号 | `calculateRoamingLocked` | 使用报文的有符号 RSSI 作当前基线，不改用页面客户端缓存 |
| `0x58` 的 BSTM 邻居字段 | `neighborSignals → candidateLocked` | 按整份邻居报告识别 RCPI/有符号 RSSI；RCPI 为整数 `value/2−110`，另一编码按 int8；估速用转换后值，候选比较用 `max(−95, dBm−10)` |
| `0x53` 独立邻居统计 | `observeRSSIStatistics → StationDB.Neighbors` | 有符号 RSSI，0 槽不入邻居表；无 BSTM 时取有效邻居，不套用 BSTM 的额外 −10；估速率按原 AC 为未知 −1 |

`0x58` 的第0个邻居若正好是当前 BSS，V6 用其修正信号和估算率更新当前基线；V4跳过该邻居但继续用触发报文的当前信号。这一差异已有两版 AC 证据，不做“统一页面数值”式的算法合并。

候选估速又与显示的协商速率分开：V4 用转换后信号加95，V6加85，随后查询原编译表和终端/AP PHY；两版均不读取 `ClientNativeRates` 或 `NegotiatedMbps` 作为这个估算入口。因此3007的协商字段为0，不会单凭这一字段关闭 BSTM 候选估算。没有 BSTM 邻居时仍按原独立表/未知率分支处理，不临时拿原生速率填补。详见[两版策略对照](cross-version-mobility-review.md)。

### AP 发送端与 AC 接收端的代码依据

- 3007 `GetPrivRssiStatistics@a0c50` 与5100HC `@e1828` 都读取独立的 `/apmng_roam/roam_msg/probe_sta_list`，并复制其每 MAC 的射频信号槽；`CWAssembleRssiStatisticsMsg@8cd80/@cc96c` 将它们放入 `0x53`。不是读取 Web 的 `sta_list.rssi`。该表填充回调 `@18ddfc/@219228` 分别处理各射频探测样本，输出前减95、写回字节；两条发送链的负值生成在 AP 内完成，Go 接收端不再减第二次。
- 两版 AP 的 `staRoamEventIndicate@1fbdc8/@276638` 都将原始漫游事件偏移 `0x0e` 当作有符号 char 扩展后传入后续事件，不经过 Web JSON 转换。这里只证明所审发送链的字段保留方式，不能据此宣称已经穷尽驱动内部全部测量/滤波算法。
- V4 AC `_roaming_nbr_packet_create@487610` 与V6 `_wsta_roam_pkt_roaming_by_rssi_low@4e6564` 的 BSTM 编码判定、转换和候选余量与 Go 一致；`stats_db_sta_get_nbr_set@66ddac/@7aef88` 是无 BSTM 的独立 RSSI 表入口。函数指纹和调用链在[跨版本证据](cross-version-mobility-evidence.json)中。
- 本轮保留的现场事件日志中，1307条 `0x58` 当前信号为−79～−61；4223个邻居原编码为10～217。后者有正数是预期的**编码字段**，不能直接当正 dBm 或原生 SNR。现场未留到可计数的 `0x53` 事件，不能用它来宣称所有回退测量已在现场覆盖。日志仅补查实际输入，不用来反推原策略。

新增回归 `TestNativeTelemetryCannotChangeRoamingDecisions` 对 V4/V6 × BSTM/独立 RSSI 表四条路径，在真实合并入口输入正、负、零和大原生信号及原生流量值，核对候选结果不变。测试故意让页面缓存信号与当前触发不同，防止实现误读显示缓存。

### 哪些行为算 bug，哪些还不能这样下结论

1. **已确认的 Go bug**：把原生流量当协商 Mbps、原生快照擦掉 CAPWAP 信号；已修复。把不同单位原值放在正常信号旁也会误导，本轮改为诊断折叠区。
2. **3007 原生字段名与单位不一致**：名字是 `rssi`，但该版输出的是驱动 SNR；5100HC 的相同接口会减95。这是确定的接口语义差异，不等于 AC 调度也拿正 SNR 比负门限，不能据此指控原 AC 的调度 bug。
3. **3007 协商字段无条件0**：确认该发送实现缺失这一遥测事实；不能说链路实际0 Mbps，也不能仅凭此证明候选估算算法出错。Go没有猜造协商值。
4. **原 AC 的 RCPI/RSSI 自动识别**：对128～219的歧义区依赖奇偶性/RSNI，冲突时整组舍弃。这是原两版的兼容算法，理论上有误判风险；没有找到编码生产者与该判断相矛盾的确定证据前，不自行替换为按型号或正负号猜测。
5. **固定噪声基准、候选 −10 和 V6 回退频段细节**：都是原活跃策略中的行为，不因为数值与 Web 看起来不同就改掉。已确认的空邻居串用前一客户端候选、V4 PMK 空输出参数问题仍保留独立缺陷证据与修复，不混为本轮信号单位问题。

这里的“统一 dBm”指统一协议语义，并不承诺两款芯片的射频校准、平滑时刻和天线合并完全相同；也不把任意型号的正原生数硬减95后当成实测 dBm。
